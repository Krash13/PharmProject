Этот файл — отправная точка контекста для ИИ-агентов и разработчиков, которые продолжат работу

## 1. Назначение проекта

PharmProject — вычислительная **воронка виртуального скрининга лекарств**. Она проводит молекулы
от ~24 млрд «lead-like» соединений из ZINC22 до десятков перспективных кандидатов с предсказанием
активности (pIC50), профилем безопасности (ADMET) и фармакокинетической моделью (PK).

Полное описание и таблица этапов — в [`README.md`](README.md). Исходный план работ —
[`work_plan.md`](C:/Users/Roman/Documents/work_plan.md) (вне репозитория).

Этапы воронки (кратко):

1. Скачать lead-like подмножество ZINC22 (~24 млрд SMILES).
2. Быстрый отсев по физико-химическим свойствам на GPU — nvMolKit (→ 1–3 млрд).
3. ADMET-фильтрация — ADMET-AI (→ ~10–50 млн).
4. Дообучить ChemBERTa на BindingDB и предсказать pIC50 (→ топ 1 000–10 000).
5. Докинг / предсказание комплекса — Boltz (→ топ 100–1 000).
6. Финальная глубокая ADMET-оценка — ADMETlab 2.0 / pkCSM (→ 10–50).
7. Трёхкамерная PK-модель на ОДУ (→ PK-модели для 10–50 кандидатов).

## 2. Ключевые ограничения (обязательно соблюдать)

- **Огромные данные.** На этапах 1–3 счёт идёт на миллиарды молекул. Никогда не загружай весь
  датасет в память. Работай **пошардово/потоково**: читай шард → обрабатывай → пиши шард.
- **Формат обмена — Parquet (Arrow).** Промежуточные результаты между стадиями хранятся в Parquet.
  Используй Polars/DuckDB/pyarrow; pandas допустим только на «маленьких» этапах (5–7).
- **Чекпоинты обязательны.** Стадии 2–5 работают на GPU часами/сутками. Каждая стадия должна быть
  идемпотентной и возобновляемой (resume), иначе сбой уничтожает сутки расчёта.
- **Дедупликация.** Между стадиями дедуплицируй молекулы по канонической InChIKey. Канонический
  SMILES (RDKit) — основной ключ соединения.
- **Защита от утечки данных.** При дообучении ChemBERTa нельзя допустить, чтобы молекулы из
  тестовой выборки (или те, по которым потом интерпретируется новизна) попали в обучение.
  Как минимум: исключить целевые активные соединения мишени из интерпретации «новых» кандидатов.
- **Детерминизм.** Фиксируй сиды (random, numpy, torch), версии пакетов и чекпоинты моделей.
- **Сеть.** При сетевой проблеме (pip, загрузка данных, внешний API) прерви работу и сообщи
  пользователю — он сам решит, что делать. Не зацикливайся на ретраях и не обходи сетевые
  ограничения.

## 4. Стек и ключевые зависимости

- Python 3.10+; пакетный менеджер и зависимости фиксируются в `pyproject.toml`.
- RDKit, nvMolKit (NVIDIA), PyTorch, HuggingFace Transformers/Datasets, ADMET-AI, Boltz.
- Polars, DuckDB, pyarrow; Pydantic v2; SciPy; NumPy; structlog; pytest.
- Трекинг экспериментов: MLflow или Weights & Biases (опционально; решим при реализации этапа 4).

## 5. Базовые концепции

- **`Stage`** — единица конвейера. Интерфейс: `run(context: PipelineContext, input: StageOutput)
  -> StageOutput`. Каждая стадия объявляет входную/выходную схему и пишет результат в
  версионированную директорию.
- **`MoleculeRecord`** — центральная модель данных. Обогащается по мере прохождения воронки:
  - базовые: `id`, `zinc_id`, `smiles` (канонический), `inchi_key`;
  - этап 2: `mw`, `logp`, `hbd`, `hba`, `tpsa`, `rot_bonds`, `qed`;
  - этап 3: 41 ADMET-параметр + флаг `admet_pass`;
  - этап 4: `pic50`, `target`, `bindingdb_training_flag`;
  - этап 5: `docking_score`, `boltz_confidence`, `complex_pdb_path`;
  - этап 6: `final_admet_*` (hERG, CYP, BBB, гепатотоксичность);
  - этап 7: `pk_params` (CL, Vss, fu, Vc, V2, V3, k12/k13/k21/k31, kel), `pk_curve_path`;
  - служебное: `provenance` (какие стадии пройдены, версии, метки времени, скоринги).
- **`Adapter`** — тонкая обёртка над внешним инструментом (ZINC22, nvMolKit, ADMET-AI, ChemBERTa,
  Boltz, ADMETlab 2.0, pkCSM). Вся «внешняя» логика живёт только здесь; стадии вызывают адаптеры.
- **`storage`** — единая точка доступа к `data/`. Схема путей:
  - `data/raw/zinc22/` — скачанные SMILES-шарды;
  - `data/intermediate/stage{N}_*/` — выходы стадий;
  - `data/artifacts/` — чекпоинты моделей (например, дообученная ChemBERTa), веса Boltz.
- **Конфигурация** — YAML + Pydantic-валидация. Мишень (`target`), пороги фильтров, пути, веса
  моделей задаются конфигом, а не хардкодом. Пороги и мишень можно переопределить при запуске
  флагами CLI (например, `--target ...` или `--thresholds mw_max=350`).

## 6. Поток данных

Каждая стадия читает Parquet-шарды из директории предыдущей стадии, добавляет/обновляет поля
`MoleculeRecord`, отбрасывает неподходящие молекулы и пишет результат в свою директорию. На
границах стадий — дедупликация по `inchi_key` и логирование счётчиков воронки (сколько вошло,
сколько вышло, распределения скорингов).

## 7. Соглашения по коду

- Типизация обязательна (type hints); где важна валидация на границах — Pydantic.
- Чистые функции для химии/PK-логики; любые обращения к GPU/сети/диску — через адаптеры/storage.
- Каждая стадия и адаптер покрываются тестами с мокированием внешних инструментов (CPU/без GPU).
- Логирование через structlog: начало/конец стадии, прогресс по шардам, метрики.
- Ошибки внешних сервисов (ADMETlab/pkCSM) — ретраи с экспоненциальной задержкой и кэширование
  ответов, чтобы не повторять запросы.

## 8. Журнал архитектурных решений

- **Единый интерфейс стадий + адаптеры** — выбрано для заменяемости инструментов и тестируемости.
- **Parquet/Arrow как формат обмена** — оптимален для колоночных данных миллиардного масштаба.
- **Оркестрация — CLI** (`python -m pharmproject run <stage>`). Решено: без Dagster/Prefect и без
  распределённого планировщика на данном этапе; при необходимости вернёмся к этому позже.
- **Без DVC** — версионирование данных и артефактов моделей через DVC не вводим. Обходимся
  версионированными путями в `data/` и зафиксированными чекпоинтами моделей.
- **Мишень по умолчанию — InhA** (еноил-ACP-редуктаза *Mycobacterium tuberculosis*, UniProt
  P9WGR1) — валидированная мишень противотуберкулёзных препаратов (изониазид). Мишень задаётся в
  конфиге и заменяется на любую другую (по имени/UniProt ID) или на собственную структуру
  (PDB) / последовательность.
- **Пороги фильтров настраиваются при запуске** (конфиг + флаги CLI), не хардкодятся. Касается
  этапов 2–4 (границы MW/LogP/ADMET, отсечка по pIC50).

## 10. Подводные камни внешних инструментов

- **Системный прокси Windows.** На машине разработки VPN прописывает HTTP-прокси в настройках
  Windows (Internet Settings), который ломает TLS-рукопожатие до `docking.org`. Поэтому все
  httpx-клиенты создаются с `trust_env=False` (прямое соединение). Не убирай этот флаг без
  необходимости и применяй то же самое в новых адаптерах, работающих с сетью.

- **ZINC22** раздаётся пошардово (транчи/slices), а не одним файлом. Загрузка = перебор шардов с
  проверкой целостности; объёмы ~24 млрд — это оценка порядка, планируй потоковую обработку.
- **nvMolKit** требует GPU NVIDIA и совместимых драйверов. Обязателен CPU-фолбэк на чистом RDKit
  для тестов и малых данных.
- **ADMET-AI** — локальный Python-пакет (FastAPI + Chemprop), предсказывает 41 параметр; работает
  быстро на GPU, но нужен свой слой батчинга/шардинга.
- **ChemBERTa** — базовая модель; точность для конкретной мишени появляется только после
  дообучения на BindingDB. Дообучение и инференс десятков миллионов молекул — отдельные шаги.
- **Boltz** — модель предсказания структуры комплекса (не классический докинг вроде AutoDock Vina).
  Здесь используется как суррогат оценки связывания; ~20 сек/молекула на A100, поэтому только для
  уже отобранных кандидатов. Веса модели скачиваются отдельно (большой объём).
- **ADMETlab 2.0 / pkCSM** — веб-сервисы: возможны лимиты, недоступность, изменение API. Кэшируй
  результаты и не строй критический путь на них без fallback.

## 11. Чего НЕ делать

- Не загружать полные датасеты в память и не использовать pandas на этапах 1–3.
- Не хардкодить мишень, пороги и пути — только через конфиг.
- Не обходить адаптеры: никаких прямых вызовов внешних инструментов внутри стадий.
- Не запускать Boltz на миллионах молекул — это финальный фильтр для топ-кандидатов.
- Не забывать про дедупликацию по InChIKey и защиту от утечки данных при дообучении.
- Не добавлять новые зависимости без фиксации версии в `pyproject.toml`.
